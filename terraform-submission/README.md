## 2. How Terraform works (step by step)

Terraform follows this workflow:

1. **init** — Downloads providers and writes `.terraform.lock.hcl` to pin exact versions
2. **fmt + validate** — Checks syntax and type correctness of your configuration
3. **plan** — Creates a dry-run execution plan showing what changes will be made
4. **apply** — Executes the plan and records the built resources in `terraform.tfstate`
5. **output** — Reads and displays the output values from your configuration
6. **destroy** — Cleans up all created resources

## 5. Step-by-step (reproduce everything)

Run from inside this folder.

```bash
# 0. (optional) personalize — copy and edit your details
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars

# 1. download providers (creates .terraform.lock.hcl)
terraform init

# 2. format and check the code
terraform fmt -recursive
terraform validate

# 3. preview the changes
terraform plan -out=tfplan

# 4. create the resources
terraform apply tfplan
#    or simply: terraform apply

# 5. read the results
terraform output
terraform output -raw deployment_id

# 6. inspect Terraform's state
terraform state list

# 7. clean up
terraform destroy
```

Each of these steps was run to produce the evidence in [`logs/`](logs) — see
section 8.

## 9. Terraform concepts demonstrated

| Concept | Where |
|---------|-------|
| Pinned provider versions / `required_version` | `main.tf` `terraform {}` block |
| Input variables with types, descriptions, defaults | `variables.tf` |
| Custom **validation** rules | `project_name`, `environment`, `tiers` |
| **loc**al values (DRY naming + tags) | `locals` in `main.tf` |
| `count` vs **`for_each`** | `for_each = var.tiers` (stable key-based addressing) |

| **`templatefile()`** | Both `.tftpl` templates |
| `jsonencode()` | `endpoints_json` / `tags_json` in the manifest |
| **Sensitive** data | `sensitive = true`, `local_sensitive_file` |
| Resource dependencies (implicit) | `random_pet` id flows into files/outputs |
| Outputs (plain + sensitive) | `outputs.tf` |
| State & change detection | `logs/07-state.log` |

## 11. Notes, cleanup and best practices

- **State & secrets.** `terraform.tfstate` can contain plaintext secrets; here it
  is included only as submission evidence. In real projects, ignore it and use a
  **remote backend** (e.g. S3 + DynamoDB locking) so state is shared and locked.
- **Lock file.** `.terraform.lock.hcl` **should** be committed; it pins provider
  versions for reproducible plans.
- **Permissions.** `output/.admin_token` is requested with `file_permission = "0600"`.
  On Windows/WSL DrvFs mounts Unix permissions are emulated, so the listing may
  show `777`; on a native Linux filesystem it is `600`.
- **Clean up** when done:

  ```bash
  terraform destroy
  ```

- **Best practices followed:** version pinning, typed & validated variables,
  consistent tagging/metadata, `for_each` over `count`, no hard-coded secrets,
  templated file generation, sensitive outputs, and a clean `.gitignore`.

## 12. Troubleshooting

| Symptom | Fix |
|---------|-----|
| `terraform: command not found` | Install Terraform and put it on `PATH`. |
| `Error: Failed to install provider` | Check internet access to `registry.terraform.io`. |
| `resource already exists` / state mismatch | Run `terraform destroy` then re-apply, or `terraform state rm <addr>`. |
| Output shows `<sensitive>` | Read it explicitly: `terraform output -raw admin_token`. |
| Permission denied writing `output/` | Ensure the folder is writable; `output_dir` is configurable. |
